# TD-54 — DB 우선, 한 번의 선택/보충

최신 제출 작업(TD-55, 2026-09-20): 현재 compact prompt는 `ce003-v3-core-experience`다. 아래 v1/v2 기록을 보존하며, 후속 32강의 내용 한계와 새 관측은 맨 아래에 구분했다. 최종 운영 적용 여부는 [제출 현황](V1_SUBMISSION.md)을 따른다.

## 결정과 목표

2026-09-19 사용자는 최초 생성 30초도 길며, 16개 전부가 완벽할 때까지 검증하는 것보다 프롬프트로 한 번에 충분히 좋은 후보를 만들고 일부 어색한 선택을 수용하겠다고 결정했다. 미리 DB에 후보를 준비하고 부족분만 보충하는 방향으로 실험한다. 모든 입력에서 완벽한 의미 정확도를 보장할 수 없다는 한계를 인정하되, 알려진 조건 위반을 의도적으로 허용한다는 뜻은 아니다.

이번 실험 목표(달성 수치 아님): 정확한 편집 preset은 로컬 worker 1초 이내/AI 0회, 새로운 16강은 단일 AI 호출 10초 안팎·$0.05 이하를 지향한다. 지연/비용 목표를 못 맞췄다면 그대로 기록한다. 소수 샘플로 p95·일반 성공률을 주장하지 않는다. 입력 다양성·명시 조건·의미 중복·비교 단위를 함께 관찰하고, 매력 차이 자체는 실패로 삼지 않는다.

기존 사례: 운영 16강은 212.375초, 6개 Responses 호출, 장부 $0.53859000였다. 첫 생성 30.794초/$0.03544550, 사실 확인 두 단계는 합계 $0.34822300다. 이는 특정 검색/수정 사례이지 16강 평균 요금이 아니다. 검색 집계의 fallback은 web_search_call action 종류를 분리하지 않으므로 장부와 최종 청구를 구별한다.

## 요청 경로

1. 기존의 명시 승인 complete-set 재사용을 먼저 확인한다. 구 certificate는 기존 정책으로만 검증한다.
2. 새 카탈로그의 **정확한 preset**이고 개인 선택 이력이 없으면 편집 후보를 DB에서 선택한다. N보다 부족하거나 재생성에서 같은 전체 세트밖에 없으면 다음 단계로 간다.
3. 그 외 요청은 SQL로 최대 64개 후보를 가져온다. 키워드는 검색 우선순위일 뿐 조건 충족 판정이 아니다. 모델 한 번이 원문 조건과 선택 이력을 고려해 DB ID를 고르고 부족한 후보만 추가한다. 후보를 새로 만들 필요가 없다면 ID만 반환한다.
4. 서버가 후보를 합치고 N·알려진 ID·이름/family 중복·단위·필드·구조를 검사한다. 실패하면 종료하며 reviewer/Repair/검색/느린 엔진을 자동 호출하지 않는다. worker crash 뒤 attempt=2는 DB 전용 복구만 허용하고 유료 보충은 거절하여 미확인 비용을 다시 쓰지 않는다.
5. 통과한 preview 이후에는 기존 freeze/게임/저장/공유를 사용한다. snapshot은 카탈로그 참조가 아니라 당시 display copy다.

`CANDIDATE_ENGINE_STRATEGY=catalog`로 명시 선택한다. 기본값 `staged`를 보존해 이번 코드 작성만으로 운영 정책을 바꾸지 않는다. catalog deadline 기본 30초(허용 1~60초), reasoning `none`, output 상한 4096, tools=[], 예약 $0.50이다. 상한은 사용 목표나 보장 응답 시간이 아니다. 같은 모델 Terra를 유지하여 구조 변화 효과부터 관찰한다.

## DB 준비와 재사용

V4에 일반 취미 32개/데이트 활동 16개/식사 메뉴 16개, 총 64개 AI 편집 seed를 넣는다. `AI_CURATED_EDITORIAL_V1`, `human_rated=false`, time-independent와 active를 명시한다. 사람 평가 통과·독립 모델 검토 통과라고 표시하지 않는다. 원래 의미가 같은 그림/악기/공예를 매체만 바꿔 개수를 채우지 않는다.

0회 preset은 `취미 추천해줘`, `데이트 활동 추천해줘`, `저녁 메뉴 추천해줘` 세 문구의 NFKC/공백 정규화 일치와 ko-KR/Asia/Seoul에만 적용한다. 조건이나 문장부호를 삭제해 강제로 적중시키지 않는다. 의미가 비슷한 문장은 일반 1회 선택 경로다. date/dinner 32강은 부족분을 한 번 보충한다.

개인 원문과 새 응답을 공용 catalog로 자동 저장하지 않는다. 새 생성 결과는 기존 private draft로 저장되지만 구 승인 complete-set certificate는 만들지 않는다. 운영자 검토·추가 seed·조건별 속성/검색 범위 확장은 후속 작업이다. 벡터 DB/임베딩/학습 작업은 도입하지 않는다.

## 실험·예산·출시 판정

`evals/catalog-cases.json`의 공개 합성 사례를 사용한다. 기존 hobby-solo 원문, 일반 데이트, 고기/매운맛 제외 저녁, 카탈로그 밖 창작, 최신 사실 거절을 구별한다. 최초 결과와 실패를 보존하고 선택 ID/보충 후보/latency/토큰/장부 비용을 기록한다. 사람 최종 품질 승인을 자동 추론하지 않는다.

일반 test/verify는 CANDIDATE_LIVE_TEST=false. 유료 실행은 같은 기존 LiveEngineHttpTest를 사용하고 CANDIDATE_ENGINE_STRATEGY=catalog, CANDIDATE_LIVE_CASE=catalog-*, 해당 강수와 실험 **남은 누적 예산**만 자식 프로세스에 주입한다. 운영 $5와 실험 $6은 별개이며 섞거나 DB 초기화로 한도를 늘리지 않는다. 검색 없음/자동 충전 OFF/.50 미확인 예약 유지. 동일 실패 수정–재검증 최대 3회, 독립 코드 리뷰 최대 2회.

배포 전 관련 단위·실제 격리 DB·HTTP 재생성/완주/공유·기존 strict/reuse 회귀·전체 verify와 독립 코드 리뷰가 필요하다. 코드 통과와 모델 의미 품질 관찰, 실제 운영 반영은 각각 구별한다.
